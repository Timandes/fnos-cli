# fnos 0.4.0 升级与完整命令覆盖设计

## 背景

fnos-cli 0.2.2 当前依赖 `fnos ^0.2.1`，通过 `COMMAND_MAPPING` 将 7 个 SDK 领域类的 26 个方法注册为 `模块.命令`。fnos 0.3.0 和 0.4.0 保留了这些类和方法，并新增 14 个领域类及 85 个方法，因此 fnos 0.4.0 一共提供 21 个领域类、111 个业务方法。

fnos 0.4.0 同时增加两步验证登录、`HTTPSRequiredError`、WSS 连接参数及 71 个新的只读查询端点。当前 CLI 的通用参数构造器只收集用户显式提供的值，再按类名决定超时参数位置；这会让缺省的可选位置参数发生错位。例如：

- `store.listDisk` 会把 `10000` 当成 `noHotSpare`；
- `network.list` 会把 `10000` 当成 `type`；
- `store.state` 会把超时值当成 `name`；
- `file.ls` 被 CLI 错误地强制要求 `--path`，而 SDK 默认允许 `null`。

仓库虽声明 `mocha test/**/*.test.js`，但目前没有 `test/` 目录。升级必须先建立可验证的测试基础，再修改生产代码。

## 目标

1. 将 SDK 依赖升级到 `fnos ^0.4.0`。
2. 保留原有 26 条命令的名称和已有参数拼写。
3. 将 85 个新增 SDK 方法全部暴露为 CLI 命令，使业务命令总数达到 111。
4. 用声明式参数元数据解决可选位置参数、默认值、类型转换和超时位置问题。
5. 支持 fnos 0.4.0 的两步验证、token 重用、WSS 和 HTTPS 重定向诊断。
6. 建立离线单元测试、SDK 导出契约测试和基于 fnos-mock-server 的 CLI 冒烟测试。
7. 更新版本、命令参考、README、CHANGELOG 和项目原则文档。

## 非目标

- 不新增 fnos 0.4.0 未提供的写操作。
- 不改变既有输出格式化规则。
- 不改变 SDK 0.4.0 的默认证书校验策略；只有用户显式提供 `--verify-ssl` 才启用证书校验。
- 不连接真实 NAS 作为自动化测试后端。
- 不把 fnos-mock-server 或其响应 fixture 复制进本仓库。
- 不在这次升级中重新设计凭证加密存储；继续依赖权限为 `0600` 的设置文件，并修正文档中不准确的“加密保存”描述。

## 方案选择

采用显式、声明式的完整命令目录。

没有采用运行时扫描 SDK 原型的方法，因为 JavaScript 运行时无法可靠获得 TypeScript 参数类型、默认值、必填性、CLI 帮助文本和业务参数位置。也没有采用只接入常用模块的增量方案，因为这会继续造成 SDK 与 CLI 能力漂移。

## 声明式命令目录

每条命令包含以下元数据：

```js
{
    method: 'listRegistryRepositories',
    description: 'List Docker registry repositories',
    timeoutPosition: 'last',
    options: [
        { name: 'keyword', flag: '--keyword <string>', type: 'string', defaultValue: '' },
        { name: 'page', flag: '--page <integer>', type: 'integer', defaultValue: 1, min: 1 },
        { name: 'pageSize', flag: '--page-size <integer>', type: 'integer', defaultValue: 20, min: 1 }
    ]
}
```

参数类型限定为：

- `string`：普通字符串；
- `integer`：十进制整数，可声明最小值、最大值或允许值集合；
- `boolean`：只接受大小写不敏感的 `true` 和 `false`；
- `csv`：逗号分隔的非空字符串数组；
- `json`：JSON 对象；
- `json-record-array`：JSON 对象数组。

参数构造器按照元数据中的完整顺序生成业务参数。未提供的可选值使用 SDK 0.4.0 的真实默认值，再按 `timeoutPosition` 把 `10000` 放在首位或末位。这样可以稳定处理多段可选位置参数，例如 `share.listLinks` 和 `docker.listRegistryRepositories`。

所有类型和范围校验在创建网络连接前完成。解析失败以退出码 `4` 返回用户友好错误。

既有缺省行为修正为：

- `file.ls` 的 `path` 默认为 `null`；
- `store.listDisk` 的 `noHotSpare` 默认为 `true`；
- `network.list` 的 `type` 默认为 `0`，且只允许 `0` 或 `1`；
- `store.state` 的 `name` 和 `uuid` 分别默认为空数组；
- `file.rm` 的 `moveToTrashbin` 默认为 `true`，`details` 默认为 `null`。

## 代码结构

命令目录按业务领域拆分，避免把 111 条定义集中到单一大文件：

```text
src/commands/
├── catalog/
│   ├── index.js
│   ├── monitoring.js
│   ├── storage.js
│   ├── system.js
│   ├── identity-security.js
│   ├── network-sharing.js
│   └── applications.js
├── index.js
├── options.js
├── runner.js
└── auth.js
```

- `catalog/*.js`：只保存领域、方法和参数元数据。
- `catalog/index.js`：合并并导出完整目录，同时提供命令计数。
- `options.js`：注册 Commander 选项、解析类型、应用默认值并生成 SDK 参数。
- `runner.js`：完成凭证解析、客户端生命周期、SDK 调用、输出和退出码映射。
- `commands/index.js`：只负责把目录注册到 Commander。
- `utils/client.js`：负责连接、登录、两步验证、token 回退和 21 个 SDK 类实例化。

CLI 入口改用异步解析。`src/index.js` 导出可测试的 `createProgram()` 和 `main()`，仅在被直接执行时自动调用 `main()`；`bin/fnos` 显式调用导出的 `main()`。命令执行通过返回值和 `process.exitCode` 传播结果，不在深层逻辑中直接调用 `process.exit()`。客户端在 `finally` 中关闭。

## 认证与连接流程

### 密码与 token

设置文件继续保存 `endpoint`、`username` 和 `password`。新凭证写入以下附加字段：

```json
{
  "credentialVersion": 2,
  "token": "...",
  "longToken": "...",
  "secret": "...",
  "secretFormat": "decrypted-v1"
}
```

只有同时满足以下条件才尝试 `loginViaToken()`：

- `credentialVersion` 为 `2`；
- `secretFormat` 为 `decrypted-v1`；
- `token`、`longToken` 和 `secret` 都是非空字符串。

token 登录失败时记录不含敏感值的调试原因并回退到密码登录。密码登录成功后使用 `client.getDecryptedSecret()` 保存解密后的 secret，不能继续保存 SDK 响应中尚未解密的 `secret`。来自 `-e/-u/-p` 的临时凭证绝不写入设置文件；来自设置文件的旧凭证在密码登录成功后升级为新格式。

`logout` 清除旧字段及 `credentialVersion`、`secretFormat`，继续保留设置文件中的非认证内容。

### 两步验证

`login` 和所有业务命令支持：

- `--twofa-code <code>`：六位数字验证码；
- `--trust-device`：提交验证码时请求信任当前设备。

验证码仅存在于当前进程，不写入设置文件和日志。

认证流程为：

1. 连接服务器；
2. 尝试可用的 token；
3. token 不可用或失败时执行密码登录；
4. `twofaRequired` 为真时验证验证码格式并调用 `submitTwofaCode()`；
5. `twofaSetupRequired` 为真时停止，并提示用户先在 fnOS 网页端绑定两步验证；
6. 只有得到最终 token 和 secret 后才把客户端视为已认证。

认证失败使用退出码 `3`。

### WSS 与 HTTPS 重定向

endpoint 可以直接使用 `wss://host:port`。`--verify-ssl` 将 `skipSslVerify` 设为 `false`；不提供时保留 SDK 0.4.0 的默认行为。

捕获 `HTTPSRequiredError` 后，错误消息包含原请求地址、重定向地址，并建议使用对应的 `wss://` endpoint。其他连接和执行错误使用退出码 `1`。

### 敏感信息日志

CLI 和 SDK 日志在写入 stderr 或文件前统一脱敏。密码、两步验证码、token、long token、access token 和 secret 的值不得出现在任何日志级别。SDK 已经格式化为字符串的认证日志通过已知字段名模式替换敏感值；无法可靠脱敏的认证调试消息直接丢弃。单元测试使用哨兵敏感值检查 stderr 和日志格式化结果。

## 测试设计

### 离线单元测试

使用 Mocha 和 Node.js `node:assert/strict`，不连接网络。覆盖：

- 111 条命令、21 个领域和命令名唯一性；
- 每条定义都有描述、有效方法名和完整参数元数据；
- SDK 0.4.0 确实导出每个领域类，实例原型确实包含目录引用的方法；
- 字符串、布尔值、整数、CSV、JSON 和 JSON 对象数组解析；
- 可选默认值、首位/末位超时和参数错位回归；
- 业务参数错误在客户端创建前返回；
- 密码登录、token 登录、token 失败回退和旧凭证升级；
- 两步验证成功、验证码缺失、验证码非法和需要绑定两步验证；
- HTTPS 重定向错误和 WSS 参数传递；
- 所有日志级别的密码、验证码、token 和 secret 脱敏；
- 无论成功或失败都关闭客户端；
- 设置清理不删除无关字段；
- 命令参考文档与命令目录一致。

### CLI 冒烟测试

冒烟测试使用 [Timandes/fnos-mock-server](https://github.com/Timandes/fnos-mock-server) 作为真实 WebSocket 后端，做法参考 [Timandes/fnos-ts-client](https://github.com/Timandes/fnos-ts-client) 和 [timandes/pyfnos](https://github.com/timandes/pyfnos)。固定 mock server 提交：

```text
d9592a05a8e07082b954921acfae3a9a915f3c01
```

运行约束：

- Python 3.11；
- `uv`；
- 地址 `127.0.0.1:5666`；
- 普通测试账户 `admin/admin`；
- 环境变量 `FNOS_MOCK_TWOFA_USERS=twofauser`；
- 串行执行，避免连接和加密状态互相干扰。

测试通过子进程调用实际的 `bin/fnos`，而不是直接调用内部函数。每个认证场景创建一个隔离的临时 `HOME`，场景内的登录和后续命令共享该目录，不同场景互不共享，也不会读取或写入用户真实的 `~/.fnos`。

冒烟套件执行：

1. 普通 `login` 并检查设置文件权限和字段；
2. 两步验证用户使用六位验证码登录；
3. 使用保存的凭证执行 token 重用路径；
4. 对 111 条业务命令逐条执行一次，必填参数使用确定性测试值；
5. 所有命令使用 `--raw`，要求退出码为 `0`、stdout 是合法 JSON，且响应不包含 `Unknown request type`；
6. 检查无效业务参数在没有发起有效业务请求时以退出码 `4` 失败；
7. 执行 `logout` 并确认只清除认证字段。

HTTPS 重定向和 TLS 证书行为不由 fnos-mock-server 提供，因此放在离线单元测试中，不伪装成 mock-server 冒烟覆盖。

测试脚本：

- `npm test`：离线单元测试；
- `npm run test:smoke`：要求固定版本 mock server 已在本地启动；
- `npm run test:all`：先运行单元测试，再运行冒烟测试。

### CI

GitHub Actions 使用 Node.js 20，并按以下顺序执行：

1. 初始化临时的 `../fnos-mock-server` Git 仓库；
2. 浅拉取并 detached checkout 固定提交；
3. 使用 Python 3.11 和 `uv sync --python 3.11` 安装 mock server；
4. 设置 `FNOS_MOCK_TWOFA_USERS=twofauser` 并后台启动服务；
5. 最多等待 30 秒确认端口 `5666` 可连接；
6. 执行 `npm ci` 和 `npm run test:all`；
7. 无论成功或失败都停止服务；
8. 失败时输出 mock server 日志。

## 验收标准

1. `npm test` 在未启动任何外部服务时通过。
2. 固定提交的 fnos-mock-server 运行时，`npm run test:smoke` 通过。
3. `npm run test:all` 报告零失败。
4. 命令目录包含 21 个领域、111 条唯一业务命令。
5. 原有 26 条命令名称保持不变。
6. 111 条业务命令均能通过实际 CLI 子进程连接 mock server，并获得已知响应。
7. 两步验证、token 重用、WSS 参数和 HTTPS 重定向错误都有自动化覆盖。
8. `npm pack --dry-run` 成功，发布包包含运行文件与命令参考，不包含测试临时凭证或 mock server。
9. `git diff --check` 无空白错误。
10. 自动化日志测试确认密码、验证码、token、long token、access token 和 secret 均未泄露。
