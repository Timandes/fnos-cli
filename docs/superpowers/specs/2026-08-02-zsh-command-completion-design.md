# fnos-cli zsh 命令补全设计

## 背景

`fnos-cli` 当前使用 Commander.js 11 注册 111 条业务命令以及 `login`、
`logout`，但没有为交互式 Shell 提供命令补全。用户需要在 zsh 中按 Tab 时，
获得命令名、选项名以及有限参数值的上下文提示。

现有业务命令来自统一的 command catalog，认证和全局选项也通过集中注册函数加入
Commander。补全必须复用这些定义，不能维护一份独立且容易过期的命令清单。

## 目标

首版支持 zsh 5.8 及以上版本，并实现以下行为：

- 补全 `login`、`logout`、`completion` 和全部业务命令；
- 根据当前命令补全业务选项、认证选项和全局选项；
- 为 boolean 参数补全 `true`、`false`；
- 为声明了 `allowedValues` 的参数补全枚举值；
- 为 `--server` 动态补全已保存的 server 名称；
- 在候选菜单中展示命令与选项说明；
- 保持普通 Tab 补全完全在 zsh 内执行；
- 提供临时启用和持久安装两种使用方式。

## 非目标

首版不实现以下能力：

- bash、fish 或 PowerShell 补全；
- 从远端 fnOS 查询磁盘、共享目录、网络接口、容器等业务对象；
- 猜测任意字符串、整数或 JSON 参数的值；
- 在 npm `postinstall` 中修改用户目录；
- 自动编辑 `.zshrc`；
- 常驻后台进程或补全守护进程。

## 方案选择

采用静态与动态混合方案。

纯静态脚本启动和补全速度快，但无法及时反映 server 列表变化。每次按 Tab 都启动
完整 CLI 虽然数据准确，却会重复加载 Commander、SDK 和日志模块。混合方案把稳定的
命令结构和有限值生成为 zsh 脚本，只为 `--server` 使用轻量只读查询，在准确性、性能
和维护成本之间取得平衡。

## 架构

### 补全模型

新增 `src/completion/spec.js`，将 Commander 命令树归一化为与 Shell 无关的补全模型。
模型包含：

- 命令名称、说明和子命令；
- 位置参数的名称、说明、必填性和有限候选；
- 可见选项的长短名称、说明和参数占位符；
- 选项是否可重复；
- 值补全类型：无固定候选、boolean、枚举或动态 server。

`completion` 使用一个可选 shell 参数，并包含 `install <shell>` 子命令。模型递归处理
命令树和位置参数，以支持：

```text
fnos completion zsh
fnos completion install zsh
```

业务命令仍是 `sysinfo.getHostName` 这样的单个命令词，不拆分为多级命令。

Commander 的命令和选项对象是名称及说明的来源。业务 catalog 中现有的 `type` 和
`allowedValues` 是值补全的来源。选项注册函数为 Commander `Option` 附加内部
completion metadata；该元数据不改变 Commander 的解析、校验或错误信息。隐藏的
legacy 选项不进入模型。

### zsh 渲染器

新增 `src/completion/zsh.js`，从统一模型生成两种格式：

1. `fnos completion zsh` 输出可被 `eval` 的完整函数定义，并通过 `compdef` 注册
   `fnos`；
2. 安装器输出以 `#compdef fnos` 开头的 zsh autoload 文件正文。

两种格式共享同一套候选数据和转义函数。渲染器使用 zsh 原生 `_arguments -C`、
`_describe` 和状态分派处理上下文，支持：

- 全局选项位于命令前或命令后；
- `--server office` 和 `--server=office` 两种写法；
- 长选项与短选项；
- 不再提示已经使用且不可重复的选项；
- `--` 之后停止选项补全。

普通字符串、整数和 JSON 参数只展示 `<name>`、`<integer>`、`<json>` 等类型说明，
不回退为本地文件补全。

### 动态 server 查询

新增 `src/completion/runtime.js`，提供内部协议：

```text
fnos __complete server
```

`bin/fnos` 在加载 `../src` 之前识别这一精确参数序列。匹配时只加载 completion
runtime 和 settings 模块；其他调用继续进入现有 Commander 主程序。`__complete`
不会注册为 Commander 命令，因此不出现在帮助或补全候选中。

runtime 每行输出一个合法 server 名称。它不加载 Commander、fnOS SDK 或 Winston，
不连接 fnOS，也不输出 endpoint、username 或任何凭证字段。

settings 模块增加只读的 server 名称读取接口。该接口：

- settings 不存在时返回空数组；
- 当前 `servers` 结构及每条凭证记录有效时返回合法键名；
- 旧版顶层凭证完整时把 `default` 作为候选，但不执行迁移；
- JSON、根对象、`servers` 对象或 server 名称结构异常时抛出配置错误；
- 不调用保存逻辑，不改变文件内容、权限、inode 或时间戳。

completion runtime 捕获这些只读错误，返回空输出和退出码 0，避免按 Tab 时污染终端。
正常候选沿用交互选择器的顺序：`default` 优先，其余名称按字典序排列。

### zsh 会话缓存

生成的补全函数维护 `_fnos_` 前缀的会话变量，缓存 server 候选及 settings 文件状态。
缓存键由 inode、大小和修改时间组成。当前 settings 保存流程使用临时文件加原子重命名，
因此 login/logout 修改配置后 inode 会变化，即使连续写入发生在同一秒也会失效。

缓存只存在于当前 zsh 进程。settings 文件不存在时使用明确的 `missing` 缓存键；文件
随后出现时会触发查询。若 `zsh/stat` 模块不可用，补全退化为每次调用轻量 runtime，
不牺牲正确性。

## 命令与安装体验

### 临时启用

已经初始化 zsh completion system 的用户可以执行：

```zsh
eval "$(fnos completion zsh)"
```

如果 `compdef` 尚不可用，生成脚本输出明确提示，要求用户先执行：

```zsh
autoload -Uz compinit
compinit
```

生成脚本本身不主动运行 `compinit`，避免重复初始化或增加不可控的 Shell 启动开销。

### 持久安装

用户在全局安装 CLI 后显式执行：

```bash
npm install -g fnos-cli
fnos completion install zsh
```

安装器原子写入：

```text
~/.fnos/completions/_fnos
```

并打印需要放在 `.zshrc` 中、且位于 `compinit` 之前的配置：

```zsh
fpath=(~/.fnos/completions $fpath)
autoload -Uz compinit
compinit
```

安装器不修改 `.zshrc`。升级 CLI 后，用户再次运行 `fnos completion install zsh`，
以生成与新版本匹配的脚本。

安装文件以 zsh 要求的 `#compdef` 首行开头，并在第二行记录生成标记：

```zsh
#compdef fnos
# Generated by fnos-cli <version>; DO NOT EDIT.
```

已有文件包含该标记时允许覆盖。目标文件存在但不是 fnos 生成时，安装器拒绝覆盖并
报告路径，由用户自行移动或删除。首版不提供 `--force`。

`~/.fnos` 和 `completions` 目录由安装器以 0700 权限创建。补全文件使用 0644；它不含
敏感信息，且凭证父目录仍限制为仅当前用户可访问。安装器拒绝把符号链接或非目录当作
安装目录，也拒绝把非普通文件当作已有目标。写入使用同目录临时文件，在重命名前设置
权限，fsync 不作强制要求，最终原子重命名；失败时删除临时文件并保留原文件。

### 不支持的 Shell

只有 `zsh` 是有效的首版 shell 名称。其他名称返回非零退出码和明确错误，例如：

```text
Error: unsupported shell "bash"; supported shells: zsh
```

## 补全行为

以下交互均不访问网络：

```text
fnos <Tab>
  -> login, logout, completion, 111 条业务命令

fnos sys<Tab>
  -> sysinfo.getHostName 等匹配命令及说明

fnos docker.listContainers --<Tab>
  -> 该命令的业务、认证和全局选项

fnos docker.listContainers --all <Tab>
  -> true, false

fnos backup.listTasks --direction <Tab>
  -> 0, 1

fnos sysinfo.getHostName --server <Tab>
  -> settings 中已保存的 server 名称

fnos completion <Tab>
  -> zsh, install
```

`login --server` 也提示已有名称，但仍允许输入新名称。动态候选只用于提示，不改变
现有 server 名称解析与校验规则。

## 错误处理与安全

- 所有写入仅由用户显式执行 `completion install` 时发生；普通 Tab 永不写文件；
- npm `postinstall` 不生成用户文件，也不修改 Shell 配置；
- 命令、选项、占位符和说明使用专用 zsh quoting 函数，禁止未经转义的字符串拼接；
- 动态 server 名称仍受现有 portable name pattern 约束，并作为独立候选传给 zsh；
- runtime stdout 只包含候选，一行一个；所有可预期配置错误静默转为空结果；
- runtime 不初始化业务 logger，防止日志文本混入候选；
- `fnos completion zsh` 的 stdout 只包含脚本，便于重定向和 `eval`；
- 安装成功信息写 stdout，错误写 stderr；两者都不会混入脚本生成命令的输出；
- 未知的 `__complete` 请求返回非零退出码，但不经过业务认证或网络路径。

## 性能评估

2026-08-02 在当前开发机、Node.js 22.23.1 上进行 40 至 80 次暖缓存进程测试，结果为：

| 路径 | 中位数 | P95 | 说明 |
|---|---:|---:|---|
| 空 Node.js 进程 | 17.2 ms | 18.5 ms | 运行时启动下界 |
| 完整 `fnos --version` | 46.4 ms | 48.6 ms | 生成命令的保守代理 |
| 仅加载 settings | 19.0 ms | 20.6 ms | 动态 server 路径代理 |
| 过滤 111 个命令 | 0.011 ms | 不适用 | 纯 zsh 简化微基准 |

另以当前命令和选项构造了约 73 KB 的保守合成脚本；zsh 解析增量约 8.6 ms。
最终脚本结构不同，因此这些数据只作为设计预算，不作为精确承诺。

预期影响：

- `eval "$(fnos completion zsh)"` 为每个新交互 Shell 增加约 55 至 65 ms；
- autoload 安装模式把脚本解析推迟到首次补全，不在每次启动时运行 Node.js；
- 普通命令、选项、boolean 和枚举补全不启动进程，候选规模下应无可感知延迟；
- server 缓存失效后的第一次补全约增加 20 至 25 ms，随后在同一 Shell 中使用缓存；
- 没有常驻进程、后台任务或持续 CPU 开销。

CI 不设置墙钟时间阈值，因为共享 runner 抖动会产生误报。测试改为验证静态路径不包含
子进程调用、动态入口不加载重模块，并在发布前保留人工微基准。

## 测试策略

### 补全模型

- 顶层模型包含业务命令、认证命令和 `completion`；
- 递归模型包含 `completion zsh`、`completion install zsh`；
- 典型业务命令包含业务、认证和全局选项；
- boolean、枚举和 server metadata 映射正确；
- hidden legacy 选项被排除；
- 原有 Commander 解析与退出码测试保持通过。

### zsh 生成

- eval 与 autoload 两种输出通过 `zsh -n`；
- 在隔离 zsh 中验证 `_fnos` 注册；
- 特殊字符和换行经过正确转义；
- 只有 server value action 引用 `fnos __complete server`；
- 生成文件设置宽松的大小上限，用于发现意外重复展开，而非限制正常增长。

测试环境没有 zsh 时，Node.js 单元测试仍执行，zsh 集成用例显式跳过并报告原因；CI
应安装 zsh，使发布分支实际执行语法和注册检查。

### 动态 server

使用临时 home 覆盖：

- 无 settings、多个命名 server、legacy default、损坏 JSON 和异常结构；
- 输出只含合法名称且排序稳定；
- legacy 查询前后文件内容、inode 和时间戳不变；
- 敏感字段的哨兵值不出现在 stdout 或 stderr；
- fast path 不加载 Commander、SDK 和 logger。

### 安装器

使用临时 home 验证：

- 创建目录和 autoload 文件；
- 文件标记、版本、权限和 zsh 语法正确；
- 重复安装安全覆盖 fnos 生成的文件；
- 外来文件拒绝覆盖；
- 模拟写入或重命名失败时不损坏原文件、不遗留临时文件；
- `.zshrc` 不存在时不创建，存在时内容不变。

### CLI 与文档回归

- completion 命令出现在帮助与顶层补全中；
- `__complete` 不出现在 Commander 命令计数、帮助或候选中；
- 原有 111 条业务命令保持不变；
- README 说明首次安装、升级后刷新、临时启用、持久安装和常见故障；
- npm 发布文件列表包含新增 runtime 模块和用户文档。

## 验收标准

实现完成需要同时满足：

1. 全部现有单元测试和新增补全测试通过；
2. eval 与安装模式在 zsh 5.8/5.9 中通过语法和基本交互验证；
3. 五个代表性 Tab 场景产生预期候选；
4. 普通补全路径无 Node.js 子进程，动态路径无网络和重模块加载；
5. server 查询只读且不泄露敏感字段；
6. 安装器不修改 `.zshrc`，不覆盖外来文件；
7. README 和命令帮助足以让全局 npm 用户完成安装及升级。

## 实施边界

本设计形成一个单独实施计划，范围限于 zsh 补全、轻量 server 候选、显式安装器、测试
和文档。bash/fish 支持以及远端业务值补全应分别设计，不能作为本功能的隐含扩展。
